①整体结论（结论先行）

如果只能选一个库作为主要参考——选 shadcn/ui。antd 降级为「个别复杂交互的逻辑参考」；两者都不作为运行时依赖引入。

最终建议

主要参考：shadcn/ui——把它的组件源码当作「行为规格说明书」：Radix 原语里最难写对的焦点陷阱、键盘导航、ARIA 标注、受控状态机，正是自研组件最容易缺失的部分；而它的视觉层（Tailwind class）则整体丢弃，替换为 Trim 已有的 Fluent token 体系。源码进仓库、无运行时黑盒、MIT 协议，与「原生 JS 重写」路线完全同构。

逻辑参考：antd——不引入代码，只在设计个别复杂交互时翻它的文档与源码：Progress（line/circle/dashboard 三态）、Table 虚拟滚动与列交互、Notification 队列策略、Segmented 分段器。antd 的 Ant Design 视觉语言与 Win11 Fluent 差异大，改皮成本高于收益。

明确不做：不引入 React / ReactDOM / Tailwind 运行时。Trim 是无框架 Electron 应用，已有 800+ 行自研 Fluent token 与 xtable 虚拟列表、modal.confirm 红色确认、ripple 动效（且已遵守 prefers-reduced-motion）——引入 React 换不来用户可见价值，还与 Mica/Acrylic 透明窗口的渲染路径叠加风险。

shadcn/ui 主要参考

  • 源码可复制：组件代码直接进你的仓库，可任意改造成 Fluent tokens，无版本升级绑架。
  • Radix 行为层：焦点陷阱、roving tabindex、ARIA、弹出层定位——系统工具高频交互的「正确性底座」。
  • Token 同构：CSS 变量风格与 Trim 的 main.css 自定义属性体系一一对应，映射成本极低。
  • 视觉层丢弃重写：Tailwind class → Fluent token，无「网页后台感」，可保 8px 圆角的系统工具气质。

Ant Design (antd) 逻辑参考

  • 优点：Progress/Statistic/Table(virtual)/Notification/Segmented 的交互模型成熟，文档全。
  • 不引入原因：必须捆绑 React 运行时；Ant 视觉语言（大圆角卡片、蓝白后台风）与 Fluent 冲突，重绘工作量>自研。
  • 用法：只在设计评审时对照其 API 设计（如 confirm 的 promise 化、进度多形态），代码不进仓库。

⑥落地路线（获批后执行）

三个阶段全部为原生实现，设计产物沉淀进仓库的 design-system/ 目录；不新增任何 npm 运行时依赖。

1
高频五件套（约 2 天）

Dialog（含红色确认 + 焦点陷阱，顺带关闭审查项 B10）、Switch、Progress（线/环）、Slider、Badge——按 shadcn/Radix 行为规格直译为原生 Fluent 组件，进 design-system/，并回替换现有页面。

2
行为层补齐（约 2-3 天）

Tooltip、DropdownMenu、Accordion、Empty 状态、Skeleton 骨架屏；统一弹出层定位与 Esc/外点关闭规范；全部接入 --fg-tertiary 等已修正的 WCAG token。

3
模块换肤收口（按模块排期）

11 个模块逐个迁移到新组件（顺序建议：设置 → 启动项 → 右键 → 优化中心 → 清理 → 其余）；xtable/modal 等成熟自研底座保留，只做行为增强；每模块迁移后跑一遍深浅色 + 减弱动效 + 1294×870 最小窗口三查。
