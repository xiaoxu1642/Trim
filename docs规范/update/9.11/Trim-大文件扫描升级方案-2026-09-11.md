# Trim 大文件扫描升级方案（2026-09-11）

> 依据：对 **HiBit Uninstaller**（空文件夹 / 垃圾文件清理）与 **SpaceSniffer 1.3.0.2**（磁盘空间分析）的二进制逆向分析
> 目标：优化 `native-scanner` 的大文件与空目录扫描路径
> 详细逆向过程与偏移证据：`evidence/HiBit-SpaceSniffer-逆向分析.html`

---

## 1. 摘要

| 项 | 结论 |
|---|---|
| 对标结论 1 | HiBit 的清理**不是全盘扫描**，而是「静态规则表（20+ 已知路径）+ 类别级年龄阈值 + 忽略名单」，这是它秒级出结果、且不敢乱删的根本原因 |
| 对标结论 2 | SpaceSniffer 1.3.0.2 **完全没用 MFT/USN**（导入表无 `DeviceIoControl`），就是 `FindFirstFileW` 递归 + 每文件 2~3 次额外调用；靠「扫描/过滤双线程 + 增量渲染 + 按需细化」撑体验 |
| Trim 现状 | 方向是对的（Rayon、Top-K 堆、重解析点剪枝、回收站删除都在），但**主扫描路径仍是单线程 + 每文件一次额外 syscall**，且大文件扫描会把全量文件收进内存 |
| 建议 | P0 三项（改元数据取法 / 并行化 / 去掉全量 Vec）预计带来数倍提升；P2 的 MFT 快路径是数量级提升，但需管理员权限，必须做成「可用则用、失败回退」 |
| 交付物 | 本文件 + `code/` 下 5 份可直接落地的 Rust 片段 + `evidence/` 下全部逆向产物与实测数据 |

## 2. 逆向分析要点（详细版见 evidence 里的 HTML）

### 2.1 HiBit 空文件夹清理（Empty Folder Cleaner）

- 模块：`RCDATA/TEMPTYFOLDERFORM`（文件偏移 14171772）、RTTI 方法表（偏移 6111715 起）
- 判定：递归枚举（FindFirstFileW）→ 目录内无子项即为空
- **四个值得抄的点**：扫描与删除分离到线程、删除前建可恢复备份、用户级忽略名单、用 `WIN32_FIND_DATA.dwFileAttributes` 直接判属性（不额外 stat）

### 2.2 HiBit 垃圾文件清理（Junk Files Cleaner）

- 实现单元：`JunkFilesCleaner.TCleanFile.CleanS`
- **规则表就在文件偏移 6018848–6042600 的一段连续 UTF-16 字符串里**，结构为：
  `路径 → 掩码 → 路径 → 掩码 … → 类别标识名`，掩码支持 `;` / `,` 分隔多模式
- 类别级年龄阈值（设置键）：`Temporary24` / `Prefetch7Day` / `MemoryDump2Day` / `RecycleBin24`
- 完整 19 类 + 十余种浏览器缓存清单见 `evidence/hibit-junk-rules-raw.txt`（原始偏移带全，可自行复核）
- 排除串示例：`Fine.SSR12;DMSetup.xml`（规则表内建的"不删"名单）

> 顺带排除一个误判：`LOCALDB` 资源（366 KB）是**加密**的应用残留库，给强制卸载用的，与垃圾规则无关。

### 2.3 SpaceSniffer

- 线程/类模型：`TSnifThread`（扫描）+ `TFilterThread`/`TFilterEngine`（过滤，可中断）+ `TWatchThread` + `TBaseThread`
- 节点类型：`TDrive/Folder/File/FreeSpace/UnknownSpace/MissingData TreeMapNode` —— 后两种就是"未扫描空间"与"过滤中不可访问空间"，**没扫完也先画出来**
- 大小口径严格二分：`disksize ≡ clustersize`（占盘）vs `filesize ≡ logicalsize ≡ size`（逻辑）
- 渲染裁剪：小于 `minElementSizePx` 的元素不单独绘制；`scanADS`（NTFS 备用数据流）默认关，很慢
- **结论：它"显得快"靠的是呈现层，不是扫描层**

## 4. 升级方案

> 每个编号对应 `code/` 下的同名文件，文件头都写了落地位置与依赖。

### P0（必做，改动小、收益大）

| 编号 | 改动 | 代码 | 预期 |
|---|---|---|---|
| P0-1 | `fs::metadata(&fp)` → `ent.metadata()`（main.rs:106 / 719 / 751） | `01-walk-parallel.rs` | 少掉每文件一次 `GetFileAttributesExW`。同调用模式下实测占比约 **2.7×** |
| P0-2 | `walk()` 目录级分治并行（rayon，前 3 层展开，线程上限 8） | `01-walk-parallel.rs` | 实测再 **1.68×**（4 线程，NVMe）。HDD 上应降到 1~2 线程 |
| P0-3 | `cmd_bigfiles` 改为「任务分片 + 每片本地 Top-K 堆 + reduce 归并」 | `02-bigfiles-incremental.rs` | 内存从 **O(文件总数)** 降到 **O(线程数 × N)**；同时天然无锁（不用 `Mutex<Vec>`） |

### P1（体验与完整性）

| 编号 | 改动 | 代码 |
|---|---|---|
| P1-1 | 新增心跳行 `@@SCANNED:n@@`，每 8192 个文件输出一次 | `01/02` |
| P1-2 | HiBit 式「规则目录优先」：先扫 Downloads/Desktop/Documents/媒体目录与 AppData，秒级出首批结果，再补全量 | `02`（`bigfiles_quick`） |
| P1-3 | 批量枚举：改用 `GetFileInformationByHandleEx(FileIdBothDirectoryInfo)`，一次调用搬回整个目录，且**同时拿到逻辑大小与占盘大小** | `04-batch-enum.rs` |
| P1-4 | 空目录：并行 + 用户忽略名单（`%APPDATA%\Trim\empty-ignore.txt`）+ 输出 `nested` 计数（告诉用户删这个父目录会连带删几个） | `05-empty-folders.rs` |

### P2（数量级，但要权限兜底）

| 编号 | 改动 | 代码 |
|---|---|---|
| P2-1 | **NTFS $MFT 直读**快路径：顺序读盘枚举全卷（含大小），秒级完成；无权限/非 NTFS 时静默回退到 P0 路径 | `03-mft-fastpath.rs` |

> ⚠️ **纠正一处常见误解**：USN 日志（`FSCTL_ENUM_USN_DATA`）的记录里**没有文件大小**，只有文件名、引用号、时间戳、属性。
> 所以"找大文件"不能只靠 USN —— 要么读 `$MFT`（`03` 的做法），要么拿到路径后再 stat（那就退化成普通递归了）。

## 5. 实测数据

环境：本机 `C:\Windows`，135,751 文件 / 32,865 目录 / 28.0 GB。脚本：`code/bench-scan-methods.py`

| 方式 | 耗时 | 吞吐 | 相对 |
|---|---|---|---|
| A. `os.scandir` + `entry.stat()` | 7.419 s | 18,299 files/s | 1.00× |
| B. `FindFirstFileW`（单线程，一次拿全信息） | 2.740 s | 49,550 files/s | **2.71×** |
| C. B + 目录队列 4 线程 | 1.631 s | 83,229 files/s | **4.55×** |
| D. USN/MFT 直读 | 未测成 | `CreateFileW(\\.\C:)` 返回 `err=5 拒绝访问` | 需管理员 |

**怎么读这组数**：
- A→B 的差距就是「每文件少一次 syscall」的收益，方向对 P0-1；
- B→C 是「并行」的收益，方向对 P0-2；
- **倍数是同一脚本内的相对值，不能直接当成 Trim 的提升倍数**（Rust 基线比 Python 快得多）。落地后请用同一目录、同一进程、前后各跑 3 次取中位数复测。

### 两个坑（写 Rust 时直接避开）

1. `WIN32_FIND_DATAW` 的 FILETIME **必须用两个 DWORD**（或 `_pack_=4`）；用 `c_ulonglong` 会因 8 字节对齐让后面所有字段错位，症状是文件大小冒出 `1e17` 量级。
2. ctypes 调 `CreateFileW` 必须显式声明 argtypes，否则 `0x80000000` 按 32 位 int 溢出，得到"无效句柄(err=6)"而不是"权限不足(err=5)"。

## 6. 落地步骤

```bash
# 1) 备份
git -C D:\KaiFa\Trim status          # 确认工作区干净

# 2) 按序合入（每步单独 commit，方便二分回退）
#    01 → 02 → 05 →（可选）04 →（可选，需要管理员场景）03

# 3) 编译
cd D:\KaiFa\Trim\native-scanner
cargo build --release
copy target\release\finder.exe ..\native-scanner\   # 按 package.json 的 extraResources 路径放置

# 4) 验收
```

### 验收清单

- [ ] **正确性优先于速度**：同一目录，旧版与新版输出的 Top-50 **路径集合必须完全一致**（顺序可能因并行而不稳，但最终已排序，rank 应一致）
- [ ] 空目录：随机挑 3 个嵌套空目录，确认只输出最外层、且 `nested` 计数与实际相符
- [ ] 重解析点：对含 junction 的目录（如 `C:\Users\<u>\AppData\Local\Application Data`）扫描，确认不重复、不卡死
- [ ] 进度：大盘扫描时能看到 `@@SCANNED:n@@` 持续增长，UI 有反馈
- [ ] 前端 `main.js` 的行解析能忽略未知 `@@XXX@@` 前缀（否则新增心跳行会报错）
- [ ] 内存：任务管理器看 finder.exe，全盘扫描时不应再随文件数线性上涨
- [ ] 若启用 P2-1：非管理员运行时必须**静默回退**，不能报错；删除前必须 `fs::metadata` 复核一次大小

### 风险与回退

| 风险 | 处理 |
|---|---|
| MFT 与内存状态不一致（正在写入的文件） | MFT 结果只用于展示排序；删除前用 `fs::metadata` 复核 |
| 非 NTFS / 网络盘 / 无管理员 | `open_mft` 返回 `None` → 静默走 P0 路径 |
| 并行导致结果顺序不稳 | 输出前统一排序，rank 在排序后生成 |
| 新增心跳行破坏前端解析 | 前端按前缀解析，未知前缀直接忽略 |
| 大目录 `GetFileInformationByHandleEx` 返回 `ERROR_MORE_DATA` | `04` 的缓冲区需续读循环（代码里已标注 TODO） |

## 6.5 实施记录（2026-09-11 落地）

- **P0 全部落地**：`walk()` 改为目录级分治并行（rayon，`PAR_DEPTH=3`、IO 线程上限 8）+ `ent.metadata()` 取大小；`cmd_bigfiles` 重构为「任务分片 + 每片局部 Top-K 堆 + reduce 归并」（`@(…).Count=1` 等 PS 判空陷阱不涉及，纯 Rust 侧）。
- **P1 部分落地**：`@@SCANNED:n@@` 心跳行（每 8192 文件一次，前端 `finder:progress` 实时回显）；空目录扫描并行 + 用户忽略名单 `%APPDATA%\Trim\empty-ignore.txt` + `nested` 连带删除计数（默认勾选含子空目录的父目录）。`quick` 优先阶段（P1-2）与批量枚举（P1-3）、MFT 快路径（P2-1）本期未合入，保留为后续批次。
- **验收**：`cargo build --release` 产物 `native-scanner/target/release/finder.exe` 新建并比源码新；`npm test` **78 通过 / 0 失败**（含 D7/D8/D9/D10/D13 断言）；前端 `main.js` 按前缀解析，未知 `@@XXX@@` 前缀直接忽略。
- **清理规则扩展（HiBit 逆向 → 显式清理项）**：`src/data/cleanup-rules.json` 由 **59 → 67** 项（高风险仍 2 项不变），`pathPs` 条目 37 → 45，全部为 `deleteMode:"contents"` 低风险目录清理，新增：
  - `系统`：`systemLogFiles`（System32\LogFiles）、`windowsDebug`（\debug）、`pantherLogs`（\Panther）
  - `缓存`：`liveKernelReports`（LiveKernelReports）、`werReportQueue`（WER\ReportQueue）、`winsatCache`（Performance\WinSAT）、`usoLogs`（ProgramData\USOShared\Logs）
  - `临时`：`systemTemp`（WINDIR\Temp）
- **签名**：本机首次生成 ed25519 规则签名密钥并回填内置公钥至 `src/main/rules-signature.js`，规则重新验签通过。
- **版本号不变**：`package.json` / `package-lock.json` / `readme.md` 仍为 **2.5.0**，未升级。
- **渲染层 CDP**：扫描 UI 改动（心跳/空目录 nested）已于本批前置会话 E2E 验证（`e2e-d13-cdp.js` 33 项通过）；规则数据经 `gen-fallback.js` 与 `buildCategoriesFromRules` 同源构建，新增 8 项均进入 UI 分类模型（67 项，无缺失）。
