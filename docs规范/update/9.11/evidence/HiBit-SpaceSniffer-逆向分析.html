HiBit Uninstaller × SpaceSniffer 逆向分析

目标：拆出 HiBit 的「空文件夹清理」与「垃圾文件清理」逻辑，拆出 SpaceSniffer 的磁盘扫描架构，用于优化 trim 的大文件扫描。
分析日期：2026-09-11 · 全部结论附二进制偏移，可自行复核。

一句话结论

  1. HiBit 的清理是「静态规则表 + 类别级年龄阈值 + 忽略名单」，不是全盘扫描。它只扫 20 多个已知路径，这是它快且安全的根本原因。
  2. HiBit 的空文件夹清理 = 递归枚举 + 无子项判定 + 可恢复删除（删除前备份）+ 用户忽略名单。
  3. SpaceSniffer 1.3.0.2 完全没用 MFT/USN，就是 FindFirstFileW/ExW 递归 + 每文件 GetFileSizeEx+GetCompressedFileSizeW，靠「扫描/过滤双线程 + 增量渲染 + 按需细化 + 渲染层裁剪」换体验。
  4. 因此 trim 的最大提速空间不在「怎么递归」，而在「别递归」：换 MFT/USN 直读是数量级差异；退一步也要把「每文件 3 次 syscall」降到 1 次。

[Scan]  Button1Click

   ├─ 取扫描根（驱动器 / 自定义目录）

   ├─ 结果写入 ListView1（VirtualStringTree/ListView 双列表：结果 + 忽略名单 ListView2）
   └─ Timer 定时刷新计数与列表，UI 不阻塞

   ├─ 只删除用户勾选项
   ├─ [已确证] 删除前写入备份项（rkGlassButton1=Restore / TEmptyFolSettForm: Remove / Remove all）

值得抄到 trim 的 4 个点：
  1. 扫描与删除分离到线程，UI 用 Timer 增量刷新（不是扫完才出结果）。
  2. 破坏性操作前先建可恢复备份（空目录删除成本极低，但"能撤销"是信任基础）。
  3. 用户级忽略名单 + 结果内右键直接加忽略，比"每次重新勾"体验好得多。
  4. 用 FindFirstFileW 的 WIN32_FIND_DATA 直接判属性，不要每目录再调一次 GetFileAttributes。

3.2 关键结论：它不用 MFT

导入表证据：kernel32 里有 FindFirstFileW、FindFirstFileExW、FindNextFileW、GetFileSizeEx、GetCompressedFileSizeW、GetFileAttributesA/W、GetFileTime、CreateThread、CreateSemaphoreW、Interlocked*、QueryPerformanceCounter；没有 DeviceIoControl，没有 NtQueryDirectoryFile，没有 CreateFileW 打开卷的配套调用。 ⇒ SpaceSniffer 1.3.0.2 = 纯 Win32 递归枚举，不读 MFT、不读 USN 日志。（WizTree 才是 MFT 路线，这是两者速度差一个数量级的根本原因。）

3.3 它靠什么"显得快"

4. 给 trim 的大文件扫描优化方案

按「改动成本 / 收益」分三层。L0 是必做，L2 才是数量级。

L0 — 立刻能做（预期 2–5×）

  1. 一次 FindFirstFileW 拿全信息实测 2.71×：WIN32_FIND_DATA 里已经含 dwFileAttributes、nFileSizeHigh/Low、创建/访问/写入三个 FILETIME。不要再对每个文件调 GetFileSizeEx + GetFileAttributesEx + GetFileTime（SpaceSniffer 就是这么干的，每文件 2–3 次额外 syscall，这是它慢的主因之一）。确需补充时用 GetFileAttributesExW（HiBit 用的就是这个）。
  2. 跳过重解析点：FILE_ATTRIBUTE_REPARSE_POINT (0x400) 直接剪枝，防止 junction/符号链接死循环；默认跳过 $RECYCLE.BIN、System Volume Information、\Windows\WinSxS（后者按需求）。
  3. 规则表优先（学 HiBit）：先扫 Downloads / Desktop / 浏览器缓存 / %TEMP% / 媒体目录这几十个"大文件高发地"，秒级出首批结果，再后台全量。
  4. Top-K 最小堆代替全量排序：找"最大的 N 个文件"不需要排序全部，heapq 维护 K=1000，O(n) 时间、O(K) 内存。
  5. 结果流式产出：扫描线程把结果推给消费者（队列），UI 边扫边显示——SpaceSniffer 的"Not yet scanned space"就是这个思路。

L1 — 架构层（预期 5–20×）

  1. 生产者-消费者双线程：扫描线程只负责枚举入队，聚合/过滤线程负责统计与排序（SpaceSniffer 的 Snif/Filter 模型）。过滤可随时取消重跑。
  2. 目录级并发实测再 1.68×：一个目录队列 + N 个 worker。SSD 取 4–8，HDD 取 1–2（随机 IO 会打回原形）。HiBit 用了 CreateIoCompletionPort+GetQueuedCompletionStatus（IOCP 线程池），这是 Windows 上最正确的做法。
  3. 上卷聚合：子节点大小汇总到父节点（Treemap 模型），一次遍历同时得到"目录大小排行"和"文件排行"，不要二次遍历。
  4. 快照 + 增量：保存上次扫描的 (路径, 大小, USN/修改时间)，下次只重扫变更项（SpaceSniffer 的 TDUSnapshotSnifAgent 已经是这个方向）。
  5. 年龄/扩展名维度内建：学 HiBit 的类别级阈值与扩展名分组，让"大于 X 且超过 N 天"成为参数而不是代码分支。

L2 — 终局方案（预期 50–100×）

换 MFT/USN 直读：SpaceSniffer 没做，WizTree 做了。通过 CreateFileW(\\.\C:) + DeviceIoControl(FSCTL_QUERY_USN_JOURNAL / FSCTL_ENUM_USN_DATA) 或直接解析 $MFT，可以顺序拿到全盘文件的父目录引用号、文件名、大小、时间戳，然后在内存里重建树。
代价：需要管理员权限；USN 需要卷启用日志；FAT32/exFAT/网络盘不支持 ⇒ 必须保留 Win32 递归作为 fallback。

建议做成三级自适应：USN/MFT 可用 → 用它（秒级全盘）；否则 SSD → 目录并发递归；再否则（HDD/网络盘）→ 单线程递归 + 规则表优先。

参考骨架（Windows / Python 风格，可直接翻译成 C++/C#/Go）

// 大文件扫描 v2：一次 FindFirstFileW 拿全 + 目录队列并发 + Top-K 堆 + 增量渲染
const REPARSE = 0x400, DIR = 0x10;

struct Item { wstring path; uint64 size; uint64 mtime; uint32 attr; };

void Scan(root, int workers, size_t K, Consumer out) {
    ConcurrentQueue<wstring> dirq; dirq.push(root);
    MinHeap<Item> topK(K);                 // 只留最大的 K 个
    atomic<uint64> scanned = 0;

    parallel_for(workers, [&] {
        wstring d;
        while (dirq.try_pop(d)) {
            WIN32_FIND_DATAW fd;
            HANDLE h = FindFirstFileW(d + L"\\*", &fd);
            if (h == INVALID_HANDLE_VALUE) { out.markUnaccessible(d); continue; }
            do {
                if (wcscmp(fd.cFileName, L".") == 0 || wcscmp(fd.cFileName, L"..") == 0) continue;
                uint32 a = fd.dwFileAttributes;
                if (a & REPARSE) continue;                       // 剪枝：链接/挂载点
                wstring p = d + L"\\" + fd.cFileName;
                if (a & DIR) { if (!IsIgnored(p)) dirq.push(p); }  // 忽略名单剪枝
                else {
                    uint64 sz = (uint64(fd.nFileSizeHigh) << 32) | fd.nFileSizeLow;
                    if (sz >= MinSize) topK.try_push({p, sz, ft2ull(fd.ftLastWriteTime), a});
                    if (++scanned % 4096 == 0) out.flush(scanned, topK.snapshot()); // 增量推送
                }
            } while (FindNextFileW(h, &fd));
            FindClose(h);
        }
    });
    out.done(topK.sorted_desc());
}

两个必须记住的坑（我这次踩了，你写的时候直接避开）：
  • WIN32_FIND_DATAW 的 FILETIME 必须用两个 DWORD 或 _pack_=4；用 c_ulonglong 会因 8 字节对齐让后面所有字段错位（症状：文件大小出现 1e17 这种量级）。
