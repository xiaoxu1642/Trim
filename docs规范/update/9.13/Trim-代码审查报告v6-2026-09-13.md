## 一、整体印象

架构清晰、安全意识很强。所有破坏性操作（文件删除、注册表清理、系统还原、进程结束）都收敛在 fail-closed 的保护判定之后；规则引擎通过**受限求值器**消除了「能写规则 JSON = 任意代码执行」；外部数据一律以 JSON 注入、解析为数据而非拼进 PowerShell 源码执行。注释中可见系统的安全批次（审查 1-1、v2.2 D1/D18、D5/D6 等），多处有「fail-closed」「纵深防御」的自觉设计。

**第二轮的核心结论**：渲染层转义**整体一致、覆盖充分**（`renderMarkdown` 先转义再套标签，AI 输出、文件路径、注册表项名全部转义）；5 个子窗口 `webPreferences` **完全统一安全**；注册表改写与文件清理均通过**快照校验 + 白名单**收口。第一轮标注的 1 项建议经复核**判定有误，本版已更正**（见第四节）。

1. **受保护路径 fail-closed 纵深防御**

   - `\\?\` 长路径前缀、8.3 短名、裸盘符、subtree/exact/anyDrive 双语义、相对路径解析异常全部 fail-closed。

   - 规则库 / 清理项 / 保护清单经 `psEscapeSingle` 后用 `ConvertFrom-Json` 解析为数据，非代码执行。

## 四、建议项（🟡 应该修复）

### 🟡 1. 在线更新后的规则库「加载时」未重新验签（纵深缺口）
- 位置：`src/scripts-powershell/cleanup-scripts.js` 第 108 行 `loadRules()`；写入侧 `main.js` 1425–1509 `cleanup:update-rules`
- 现象：**写入链路验签完备**（尺寸 → ed25519 → JSON 结构 → 条目形状 → 防降级，见 1438–1451）。但 `loadRules()` 每次从磁盘读 `%APPDATA%\Trim\cleanup\rules.json` 时**只按 mtime 做缓存、不重新验签**（第 102–108 行）。
- 影响：若攻击者能在用户配置目录写入/替换该文件（下载后再篡改，或本地低权限进程），可注入未签名规则。爆炸半径受 `Test-PathProtected` fail-closed 限制（只能删非保护路径下的数据），但纵深不足。
- 建议：`loadRules()` 加载数据目录规则时也调用 `verifyRulesSignature`，把验签结果并入缓存签名键（`mtime|size|sig`），避免每次解密的开销；与写入侧共用同一校验函数。
- **状态：✅ 已修复（2026-09-13）** —— 新增 `readVerifiedDataRules()`，`loadRules()` 第 136 行改为 `readVerifiedDataRules() || safeReadJson(RULES_FILE)`；验签失败即 `console.warn` 并回退内置规则（fail-closed）；缓存键加入文件 `size` 防「保留 mtime 的篡改」。仅校验**数据目录**文件，不校验内置文件（原因见第八节新发现）。

### 🟡 2. 自定义规则目录不验签，缺少导入风险提示
- 位置：`cleanup-scripts.js` `loadRules()`（第 110–113 行读 `%APPDATA%\Trim\cleanup\custom\*.json` → `mergeRules`）
- 现象：自定义规则完全不验签（设计如此，且合并后仍受保护清单约束）。但导入自定义规则时 UI 缺少明确的「将以你的完整用户权限运行、仅系统根受保护」提示。
- 建议：导入自定义规则时弹一次确认，明确告知权限与爆炸半径。

### ~~🟡 3. `maintenance:run` 失败时可能误报成功~~（第一轮误判，本版撤销）
- 复核结论：**该条判定错误，`maintenance:run` 实际是正确 fail-closed**。
- 证据：`main.js` 5175 行 `let result = 'ok'`；5198 行 `if (code !== 0 && result === 'ok') result = 'warn'`；5200 行 `return { success: result === 'ok', ... }`。**退出码非 0 时 `result` 必然被降为 `warn`，`success` 即为 `false`**；即便脚本显式输出 `@@RESULT@@ok`，只要退出码非 0 也会被降为 `warn`。第一轮误读为「success 仍为 true」，予以更正。

## 五、小改进（💭 锦上添花）

1. **`deviceinfo.js:22` 硬件字符串未转义**（第二轮新增）：`text(value)` 直接进 `innerHTML`，而 `system/processor/graphics/motherboard/disks/monitors/memory` 来自 WMI/固件。虽然硬件名被注入 HTML 的概率极低，但与本项目「处处 `escapeHtml`」的惯例不一致。建议补上转义以保持一致与纵深。
   - **状态：✅ 已修复（2026-09-13）** —— 新增 `esc()`，第 22 行改为 `${esc(text(value))}`（`label` 为硬编码常量，无需处理）。

2. **`optimizer-scripts.js buildScript` 的 here-string 边界**（第二轮新增）：`s.reg` 走 PowerShell 单引号 here-string `@' … '@`（2048–2050 行）；若某天 `s.reg` 变为动态内容且含独立一行 `'@`，会提前闭合 here-string 造成代码注入。当前 `s.reg`/`s.cmd`/`s.pwsh` 全部来自白名单 `OPTIONS`，**不可利用**；建议在「reg 内容转为动态」时先断言不含 `'@` 行，并在注释里固化该前提。

3. **已知死代码（行为缺陷，非安全）**：`cleanup-scripts.js` 约 655–660 行，`candidates`/`globCandidates` 分支读的是不带 `Ps` 后缀的键，而规则 JSON 实际用 `candidatesPs`/`globCandidatesPs`，导致网抑云/QQ/抖音缓存候选路径回退、微信缓存通配候选整体失效（已自注为 D19 待修）。

4. **未设置全局 `setPermissionRequestHandler`（deny-all）**（第二轮新增）：应用只加载本地页面、不请求摄像头/麦克风/定位，Electron 默认放行的风险极低。建议在 `session.defaultSession` 上显式拒绝一切权限请求，作为零成本加固。
   - **状态：✅ 已修复（2026-09-13）** —— `main.js` 新增 `session` 导入，在 `app.whenReady` 中设置 `setPermissionRequestHandler`：**仅放行剪贴板**（`clipboard-read` / `clipboard-sanitized-write` / `clipboard-write`，供 `cleanup.js`/`quickcmds.js` 的 `writeText`），其余一律拒绝。（注：报告原建议「拒绝一切」会误伤复制功能，实现时已放行剪贴板。）

5. **`contextmenu:open-in-regedit` 接受任意 `regPath` 字符串**（第二轮新增）：仅做单引号转义后作为 `$key` **数据**使用（非代码执行，无注入面），但未校验是否为合法注册表路径。最坏情况是写入一个奇怪的 `Regedit\LastKey` 并打开 regedit，风险低。可选：加根键白名单校验。

6. **`paths:file-icon` 允许任意绝对路径的 `.ico/.exe/.dll`**（第二轮新增）：注释表明为「固定图标路径兜底」有意为之，仅提取图标 dataURL，信息面很低。可接受。

7. **`quickcmds:run` 用 `exec(\`start "" ${item.cmd}\`)`**：`item.cmd` 来自编译期白名单常量，无注入面；若未来 `quickcmds-data` 改为外部数据源需立即改 `spawn`。当前注释已标明前提。

8. **`isPrivateApiUrl` 自承无法防御 DNS rebinding**：若支持本地模型端点（Ollama）需显式加白，不要直接删校验。

9. **SCAN / EXECUTE 两个 PS 模板各自内联了完全一致的 `Get-PathStats` 等函数**（数百行重复）：可抽成共享 PS 片段由主进程拼接，减少两源漂移（目前靠 `test-features` 双源断言兜底，已较稳）。

10. **`optimizer:backup-reg` 的 `steps` 入参为死参数**：`preload.js` 暴露 `backupReg(optionId, steps)`，主进程 2355 行解构后**未使用** `steps`（改从白名单按 `optionId` 推导目标）。这是安全的选择，但属 API 语义不一致，建议清理 preload 形参或注释说明。

## 八、新发现与未执行的后续项

### 🟡 新发现：内置 `src/data/cleanup-rules.json` 当前验签**不通过**
- 证据（本次实测）：用内置公钥 `verifyRulesSignature()` 校验该文件返回 `{ ok:false, reason:'签名校验失败，内容可能被篡改，已拒绝' }`；而 `scripts/sign-rules.js` 的签名与验签共用同一个 `canonicalBodyText` 且签名后会自验，因此**正确签名的文件必然验签通过** → 说明该内置文件是在签名之后被修改过（发布机未重跑 `node scripts/sign-rules.js sign`），或 `gen --force` 换钥后未重签。
- 当前影响：**低**。应用从不校验内置文件（只校验数据目录产物），故功能不受影响；但它是一个「发布产物与签名不一致」的隐患。
- 为何它反而印证了本次修复的安全性：正因内置文件验签失败，**若当初把 🟡1 实现成「连内置也校验」，应用将加载 0 条规则**。本次实现只校验数据目录文件，是正确的边界选择。
- 建议：发布前对 `src/data/cleanup-rules.json`（及 `scripts/gen-fallback.js` 产出的 fallback）执行一次 `node scripts/sign-rules.js sign` 并提交；或在 `prebuild` 钩子里加签名自检（私钥仅发布机持有，注意不要入库）。
